Technical Architecture
A complete explanation of how the AI receptionist works — from a caller speaking into their browser microphone to an appointment being written to the database, in every language mode.
Stack: Python · FastAPI · Whisper · Edge-TTS · Gemini/Groq/Ollama Modes: English (8000) · Urdu (8001) · Bilingual (8002)
Section 01

System Overview

Sara AI is a real-time voice receptionist. A caller opens a browser page, clicks "Start Call," speaks naturally, and Sara handles the entire appointment booking conversation — collecting name, phone, symptoms, doctor preference, date, and time — before writing the appointment to a database. There is no IVR menu, no hold music, no typed forms. It works entirely by voice.

The system runs as three separate FastAPI applications on three ports, all in the same Python process. Models (Whisper, VAD, TTS) are loaded once at startup and shared across all three servers via class-level state on CallHandler. This means the heavy GPU work of loading Whisper happens once regardless of how many language modes are active.

Every call flows through the same pipeline: the browser captures raw PCM audio and streams it over a WebSocket. On the server side, a Voice Activity Detector (VAD) watches the stream and identifies when the caller is speaking. Once the caller finishes a sentence (detected by a silence gap), the accumulated speech buffer is sent to Whisper for transcription. The text then passes through a quality filter, a semantic validator, a dialogue policy, and arrives at either the Fast Dialogue Engine (for structured inputs like phone numbers) or the LLM Agent (for open-ended turns like describing symptoms). The LLM's response text is streamed sentence-by-sentence to the TTS engine, which synthesizes audio and streams it back to the browser in real time.

The entire pipeline from end-of-speech to first audio byte typically takes 1.5–3 seconds: ~0.4s for Whisper transcription + ~0.8s for LLM first token + ~0.3s for TTS synthesis. A micro-acknowledgment ("جی..." / "Okay...") is played from cache immediately while the LLM generates, masking the latency.
Section 02

Ports & Entry Points

The three servers are created by calling create_app(language) with different language strings. The factory function returns a FastAPI application with a root route that serves the appropriate HTML frontend.

PortModeFrontendLanguage behaviour
8000 English index.html All STT and TTS in English. LLM uses English system prompt. Gemini skipped; Groq → Ollama chain.
8001 Urdu index_ur.html Whisper forced to Urdu language detection. TTS uses ur-PK-UzmaNeural. LLM uses Urdu system prompt. Gemini → Groq → Ollama.
8002 Bilingual selector index_select.html Sara greets bilingually and asks the caller to choose. On detection, switches language in-place on the same WebSocket — no reconnect.

Each server also exposes REST endpoints for the admin dashboard: /api/appointments, /api/doctors, /api/departments, /api/slots, and /api/knowledge. Uvicorn runs at log_level="warning" to suppress INFO-level startup noise.

Section 03

Audio Pipeline

The browser captures microphone audio using the Web Audio API: a MediaStreamSource feeds into a ScriptProcessor node running at 2048 samples per callback. Each callback converts the float32 PCM samples to a Float32Array, serialises them as raw bytes via ArrayBuffer, and sends them over the WebSocket to the server.

On the server, CallHandler.process_audio_chunk() receives each chunk. It normalises very quiet audio (if peak amplitude < 0.1, it boosts it proportionally) and passes the chunk to the VAD. Simultaneously, the chunk is added to a rolling pre_buffer — a deque of the last 300 ms of audio — which is prepended to the speech buffer when a new utterance begins. This ensures the first syllable of a word is never clipped.

When speech ends (VAD returns False after VAD returned True), the handler checks whether the silence duration has exceeded _silence_gate — 2.0 seconds for Urdu/Roman Urdu, 1.5 seconds for English. If yes, a turn-processing coroutine is spawned as an asyncio.Task.

Barge-in suppression

While Sara is playing audio, her voice echoes into the caller's microphone. Without protection, the VAD would detect Sara's own speech as user input and trigger a spurious turn. To prevent this, the handler tracks an estimate of when Sara's audio will finish playing. Each time audio bytes are added to the outbound queue, _extend_playback_guard() computes the audio's duration (bytes ÷ 16,000 bytes/s for Edge-TTS MP3 at ~128 kbps) and adds a 0.6-second margin. Any VAD positive during that window is silently discarded.

Interruption handling

If the caller speaks while Sara is still generating a response (i.e., a turn task is running), the barge-in guard does not apply — the caller genuinely wants to interrupt. When VAD fires and a _turn_task is active, the task is cancelled immediately, an {"type":"interrupt"} JSON signal is sent to the browser (which stops audio playback), and the caller's new speech is processed fresh.

Section 04

Voice Activity Detection

The VAD uses Silero VAD, a small neural network (~1 MB) trained specifically to detect human speech in noisy conditions. It operates on 30 ms frames at 16 kHz and returns a probability that the current frame contains speech. The VADDetector class wraps Silero with a threshold gate — frames above the threshold are considered speech.

Silero is chosen over simple energy thresholding because it handles background noise reliably: a fan running in the room, street noise, or a quiet voice all produce different energy levels, but Silero classifies them correctly based on learned spectral patterns rather than raw volume.

The detector maintains state across chunks so it does not reset between 20 ms audio callbacks. When a call ends, vad.reset() clears that state so the next call starts clean.

Section 05

Speech-to-Text

Transcription uses Whisper large-v3 via faster-whisper, a CTranslate2-based reimplementation that runs significantly faster than OpenAI's original Pytorch version. The model runs on CUDA in int8_float16 quantisation — this halves VRAM usage with negligible accuracy loss compared to full float16.

The transcription runs in a thread pool executor (loop.run_in_executor(None, ...)) so it does not block the asyncio event loop while the GPU is working. This allows the WebSocket to keep receiving audio and the response queue to keep sending audio to the caller even while Whisper is processing.

Language handling

In Urdu mode, Whisper is called with language="ur", which forces its internal beam search to decode in Urdu. This dramatically improves accuracy for Urdu speech compared to auto-detection, which Whisper sometimes confuses with Arabic or Hindi.

In bilingual mode (port 8002), before the caller has chosen a language, Whisper is called with language=None and return_language=True. This returns both the transcript and Whisper's internal audio-language classification — a value like "ur" or "en" with a probability. This audio-level detection is used as a ground-truth signal because it operates on raw acoustic features, not the transcribed text. It correctly identifies Urdu even when Whisper transcribes it phonetically into Latin characters (e.g., "or do" instead of "اردو").

Confidence scoring

Whisper returns a log-probability score for the transcription. This is converted to a linear confidence value and passed to the STT Filter described next. Low confidence typically indicates the caller was too quiet, spoke over background noise, or the speech was too brief to decode reliably.

In phone mode (phone_mode=True, used for Twilio calls), the audio arrives at 8 kHz and is upsampled to 16 kHz before being passed to Whisper. The flag also adjusts Whisper's beam search parameters for telephone-quality audio.

Section 06

STT Quality Filter

Even a confident Whisper transcription is not always usable. The STT Filter (src/pipeline/stt_filter.py) applies three independent checks before the transcript reaches the dialogue layer:

Confidence threshold

The transcription confidence must exceed a minimum value: 0.40 for Urdu (where audio is inherently harder to transcribe due to code-switching and dialect variation) and 0.50 for English. Transcripts below this threshold are rejected and Sara asks the caller to repeat.

Length check

Transcripts shorter than a minimum character count are rejected. A single character or two-character "transcript" almost always represents Whisper hallucinating from noise rather than real speech.

Gibberish detection

Whisper sometimes generates plausible-looking but meaningless text when confronted with sustained noise — for example, a long sequence of repeated punctuation, or a string of random consonants. The gibberish detector uses heuristics based on character n-gram frequency and known hallucination patterns specific to Whisper to identify these cases.

When any check fails, Sara plays a retry prompt directly from TTS (bypassing the LLM entirely) and the turn ends. This prevents garbage transcripts from confusing the dialogue state machine.

Section 07

Semantic Validation & Dialogue Policy

After STT passes quality checks, the transcript goes through two gating layers before reaching the LLM.

Semantic validation

The semantic validator (src/dialogue/semantic_validator.py) checks whether the caller's input is meaningful in the context of the current dialogue state. For example, if Sara just asked "What is your name?", and the caller responds with a long sentence containing no name-like words, the validator flags this as semantically invalid and forces the intent to GARBAGE. This prevents the LLM from trying to parse nonsensical inputs and generating confused responses.

Dialogue policy

The DialoguePolicy evaluates the detected intent against the current dialogue state and decides whether to proceed normally or trigger a hard fallback. A hard fallback fires when the caller is clearly off-topic or confused in a way that the LLM cannot recover from gracefully. In this case, the policy generates its own fallback response text and plays it directly — the LLM is never called.

The policy also maintains the canonical dialogue state (ASK_NAME, ASK_PHONE, ASK_SYMPTOM, ASK_DATE, ASK_TIME) and synchronises it with the agent's _collected dictionary via policy.sync_from_collected(). This matters because the Fast Engine can advance the agent's internal state without going through the policy, so the policy must re-derive its state from what has actually been collected rather than relying on its own transition history.

The policy also produces two outputs used by the LLM: policy_state (the current booking step) and nlg_constraint (instructions for Natural Language Generation — for instance, "ask for the date in a short, clear sentence").

Section 08

Intent Detection

Intent detection (src/llm/intent.py) is a lightweight rule-based classifier that runs before the LLM to categorise the caller's utterance. It does not use an LLM — it works with keyword matching, pattern heuristics, and character-set detection. This keeps it fast and deterministic.

The main intents it distinguishes:

  • provide_name — short input with a name-like structure
  • provide_phone — contains digit sequences matching Pakistani mobile formats
  • describe_symptoms — contains medical vocabulary or body-part words
  • choose_date — contains date words (day names in Urdu/English, relative words like "kal", "tomorrow")
  • choose_time — contains time patterns or Urdu time-of-day words (صبح, شام)
  • confirm — affirmative words (جی, ہاں, yes, okay, bilkul)
  • deny — negative words (نہیں, no, galat) — triggers correction flow
  • unclear — nothing matches; LLM handles it

For language switching in bilingual mode, detect_language_preference() checks the transcript for the words "english", "urdu", Urdu-script Arabic characters, and phonetic variants. It returns "en", "ur", or None. When it returns None but Whisper's audio-level detection returned "ur", that audio signal is used as the tie-breaker.

Section 09

Fast Dialogue Engine

The FastDialogueEngine (src/dialogue/fast_engine.py) is a rule-based engine that handles structured booking inputs without any LLM call. It makes responses instantaneous for the most common turns in a booking conversation.

When the dialogue state is one of collect_name, collect_phone, collect_date, collect_time, or confirm_booking, the Fast Engine's try_handle() method is called first. If it can extract the expected value from the transcript, it returns a complete response dict immediately. If it cannot (the input is ambiguous, the caller seems confused, or the format is unrecognisable), it returns None and the LLM handles the turn.

Name extraction

Strips known filler phrases ("میرا نام ہے", "my name is", "I am") from the transcript, then validates what remains: it must be 1–4 words, contain no digit strings, and not match a list of non-name Urdu words (ہاں, جی, etc.) or medical vocabulary. Names that are too long are rejected as sentences.

Phone extraction

Uses three regex patterns: a full Pakistani mobile format (0 + 3xx + 7 digits), an 11-digit sequence starting with 03, and a fallback that extracts any 10–11 digit run from the transcript (for when the caller says digits slowly with pauses). This makes the engine robust to all common ways callers dictate phone numbers.

Date extraction

Recognises Urdu day names (پیر، منگل، بدھ), English day names, relative terms in both languages ("آج", "کل", "today", "tomorrow", "parso"), and numeric formats like "15/6" or "15 June". Relative terms are resolved to an absolute date object. Unrecognisable date formats defer to the LLM.

Time extraction and slot validation

Parses spoken times including Urdu number words (دس بجے → 10:00), meridiem indicators (صبح → AM, شام → PM), and numeric patterns like "10:30". After parsing, it validates the extracted time against available DB slots for the chosen doctor and date. If the exact time is not available but a slot within 30 minutes exists, it snaps to the nearest slot. If no match is found, it defers to the LLM.

Confirmation chaining

When the Fast Engine collects the last piece of information (appointment time), the agent's _compute_flow_state() returns confirm_booking — meaning all required fields are now present. Rather than waiting for the caller to speak again, the handler immediately falls through to an LLM call with a neutral trigger ("جی"), which, combined with the ALL_INFO_COLLECTED context hint, causes the LLM to generate the booking summary without requiring another user turn.

Section 10

LLM Agent (HospitalAgent)

The HospitalAgent class (src/llm/agent.py) is the central intelligence of the system. It maintains the booking state, builds LLM prompts, parses LLM responses, and executes bookings. One instance is created per call session.

System prompt

The system prompt is built fresh for each LLM call via _build_system_prompt(lang). It contains:

  • Sara's persona and role description
  • Current date, time, and tomorrow's date (so the LLM can resolve relative dates correctly)
  • Complete list of active doctors with their department, specialty, and fee
  • A strict booking flow with numbered steps in the correct language
  • Output rules including language enforcement ("Urdu script only — zero English"), tone guidance, banned formal words (براہ کرم, جناب), and punctuation rules
  • Worked examples showing the expected conversational style
  • Knowledge block: hospital hours, departments, payment methods
  • JSON output format specification

For Urdu, the system prompt is written entirely in Urdu. This is intentional — giving an Urdu model an English system prompt and asking it to respond in Urdu produces code-switching. An Urdu system prompt produces pure Urdu output.

Context injection

_build_context_injection() adds live information to the system prompt at call time:

  • The current state of _collected (what has been gathered so far)
  • Available DB slots for the chosen doctor and date range
  • The ALL_INFO_COLLECTED hint when all required fields are present, instructing the LLM to generate a booking summary
  • An instruction to exclude fee and WhatsApp details from the summary (since those are added by hardcoded code, not the LLM)

Streaming response parsing

process_turn_stream() is an async generator. It streams the LLM response token-by-token and uses a regex to detect sentence boundaries in the "speech" field of the JSON as it arrives. Completed sentences are yielded immediately for TTS synthesis, so the caller starts hearing Sara's voice before the LLM has finished generating the full response. This is how the system achieves low perceived latency even with large LLM responses.

Data collection

The LLM returns a JSON object on every turn: {"speech":"...","action":"ask|confirm|save|end","data":{"patient_name":"...","patient_phone":"...",...}}. After each turn, the data field is merged into self._collected. Placeholder values ("", "N/A", "unknown") are discarded. A normalisation step cleans phone numbers, resolves relative dates to ISO format, and validates doctor names against the DB.

State machine

_compute_flow_state() derives the current booking step purely from what is missing in _collected. It does not maintain a separate transition history — it always recomputes from the actual data. This makes the system self-correcting: if the LLM hallucinates a value that later gets cleared (e.g., user says "wrong doctor"), the state machine automatically steps back to re-collect that field.

Doctor name auto-extraction

If the LLM mentions a doctor name in its speech but forgets to include it in the data field (a common LLM omission), _try_extract_doctor_from_speech() scans the speech text for known doctor names and populates collected["doctor_name"] automatically.

Section 11

LLM Fallback Chain

All LLM calls go through _chat_stream(), which tries providers in order and falls through if any fail.

Gemini (Urdu / Roman Urdu primary)

Google Gemini (gemini-3.5-flash) is the primary model for Urdu because it produces natural, idiomatic Pakistani Urdu better than smaller models. Up to six API keys are configured, each used in rotation. A set of exhausted keys is maintained in process memory — keys that have hit their daily quota are skipped for the rest of the day without being retried. Each Gemini request has a 12-second timeout via asyncio.wait_for; if the key does not respond within that window, the next key is tried immediately. This prevents the 30–60 second hangs that occur during Gemini 503 overload events.

Groq (universal fast fallback)

When all Gemini keys fail, time out, or return 503s, Groq is tried next. Groq runs llama-3.1-8b-instant on their inference hardware and typically responds in 1–2 seconds. It handles both Urdu and English. A 10-second timeout is applied. Because Groq's model is smaller than Gemini's, its Urdu output may be slightly less idiomatic, but it is vastly better than waiting two minutes for an overloaded Gemini key.

Ollama (local final fallback)

Ollama is the last resort — a locally running LLM server. For English, Ollama is the primary (Gemini is skipped entirely for English). The configured model is tried first; if VRAM is exhausted, Ollama is retried with num_gpu=0 to run on CPU. Ollama has no timeout since a local call should always eventually return, though it may be slow on CPU.

The max token limit for Groq calls is 600 (vs 1200 for Gemini) because Groq's context window pricing makes shorter responses more economical, and Sara's responses should be brief conversational phrases anyway.
Section 12

Text-to-Speech

The VoiceSynthesizer (src/tts/synthesizer.py) uses Microsoft Edge-TTS as its primary synthesis engine. Edge-TTS is a free neural TTS service accessible via a WebSocket API without an API key. It produces high-quality voices for both English and Urdu.

For English, en-US-AriaNeural is used. For Urdu, ur-PK-UzmaNeural — a Pakistani Urdu female voice that matches the expected accent for a hospital in Pakistan.

Streaming synthesis

TTS synthesis is streaming by design. The LLM agent yields text sentence-by-sentence; the call handler synthesizes each sentence as it arrives and immediately puts the audio bytes in the response queue. The browser starts playing the first sentence while the LLM is still generating the second. This pipeline parallelism is why callers hear Sara's response within a second of speaking even for multi-sentence responses.

Tone variants

Edge-TTS supports SSML-based speaking styles. The synthesizer maps an internal policy_tone parameter (values: empathetic, question, confirm, micro) to different SSML styles. empathetic is used when Sara is responding to described symptoms; question is applied to turns that end with a question.

Persistent audio cache

Synthesized audio is cached on disk with an MD5 hash of the text+voice+tone as the key, stored in data/tts_cache/. On a cache hit, the audio is returned from disk with zero network latency. Greeting audio is cached separately in data/cache/ by the greeting text hash and reused across calls. Bilingual greetings are excluded from the greeting cache because they use mixed voice switching per sentence.

Micro-acknowledgment cache

Short filler words ("جی...", "اچھا...", "Okay...", "Mhm...") are pre-synthesized on first use and kept in memory (CallHandler._ack_cache). Each turn, one is randomly selected and played immediately, before the LLM responds. This gives callers the impression that Sara is already listening and thinking, reducing perceived silence.

F5-TTS (optional)

If f5-tts is installed, the English voice can be replaced with a voice cloned from a reference recording in voices/receptionist.wav. This would give Sara a custom voice identity. Currently the package is not installed and the system falls back to Edge-TTS for English.

Section 13

Bilingual Mode

When a caller connects on port 8002, a HospitalAgent is created with language="bi". The agent initialises with _bilingual_mode=True, _language_chosen=False, and language="en" (English is the base language for bilingual mode since the greeting is partly English).

Sara's bilingual greeting is rendered differently: sentences containing mostly Urdu characters are synthesized with ur-PK-UzmaNeural, and sentences without are synthesized with en-US-AriaNeural. This gives the greeting a natural code-switched sound rather than one voice trying to pronounce both scripts.

On the caller's first response, process_turn_stream() enters the bilingual-selection branch. Whisper is called with language=None to auto-detect. The transcript is analysed by detect_language_preference(). If the text alone is ambiguous (e.g., Whisper transcribed Urdu speech as "or do"), the Whisper audio-language value overrides the text result.

Once language is determined, the agent sets self.language, self._language_chosen = True, and self._bilingual_mode = False. It yields a short acknowledgment ("جی ضرور!" or "Sure!") and a final dict with action="switch_language".

The call handler receives this action and performs five updates in-place: sets self.agent.language, sets self.agent._fast_engine.language (critical — the Fast Engine has its own language copy for response template selection), updates self.language, updates the TTS voice, and adjusts the silence gate. It then calls agent.get_greeting() to generate a proper greeting in the chosen language, synthesizes it, and queues it. From that point, the call proceeds exactly as if the caller had connected to port 8000 or 8001 directly — no disconnect, no reconnect, same WebSocket.

The _fast_engine.language update is the most critical piece. Before this fix was added, the Fast Engine still had language="en" after a bilingual switch, causing it to return English responses like "Thank you. What's the reason for your visit?" in what was supposed to be a Urdu call.
Section 14

Call Handler Orchestration

The CallHandler class (src/pipeline/call_handler.py) is the central orchestrator for a single call session. It owns the audio pipeline, the response queue, and all the per-call state.

Response queue

The handler uses an asyncio.Queue as the outbound channel. Items on the queue are either ("audio", bytes) tuples (raw MP3 audio to send to the browser) or ("json", dict) tuples (control messages like transcript notifications, processing indicators, and action signals). A None sentinel ends the stream.

The consume_responses() generator drains the queue using while True (not while self._is_active). This is important: when _is_active is set to False by an action (like the call ending), items already on the queue must still be delivered. If the loop exited on the _is_active flag, redirect messages or final audio could be silently dropped before reaching the browser.

Turn processing

_process_turn() is the main per-turn coroutine. It runs the full pipeline — STT, filter, semantic validation, policy evaluation, micro-ack, LLM/Fast Engine, TTS — and enqueues results. It is protected by a _processing flag to prevent two turns from running concurrently. An asyncio Task wraps each call, enabling cancellation on barge-in.

Confirm reminder injection

When the LLM agent returns action="confirm", the handler calls _play_confirm_reminder() immediately after the LLM's summary audio. This method fetches the doctor's fee from the database, constructs a hardcoded line in the correct language stating the fee, WhatsApp payment instruction, and a "shall I confirm?" question, synthesizes it, and queues the audio. The LLM never knows about the fee or WhatsApp — this information is always injected by the handler. This prevents the LLM from hallucinating fee amounts or omitting the WhatsApp instruction.

Section 15

Special Features

Inactivity monitor

After a booking is completed (flow_state = "post_booking"), Sara asks if there is anything else she can help with. If the caller goes silent, the call would hang indefinitely without intervention. The _inactivity_monitor() coroutine runs as a background asyncio.Task throughout the call. It wakes every second, checks whether the flow state is post_booking and whether the time since _last_activity_ts exceeds 10 seconds. If both are true, it synthesizes a farewell, queues the audio, and closes the call. _last_activity_ts is reset any time the user speaks or Sara finishes a response turn, so the timeout only fires when there has been genuine silence since the last exchange.

Pre-speech buffer

The rolling pre-buffer stores the last 300 ms of audio at all times, regardless of whether the VAD is detecting speech. When a new utterance begins (VAD transitions from False to True), the pre-buffer contents are prepended to the speech buffer. Without this, the first 100–200 ms of a word — its onset — is lost because the VAD needs a few frames to confidently classify the signal as speech. The pre-buffer ensures Whisper receives the complete utterance including the onset consonant.

History management

The agent's conversation history is capped at 16 messages (8 turns). Older messages are truncated. This balances context (the LLM needs to remember what was discussed earlier in the call) against token cost and the risk of the LLM becoming confused by very long contexts in which the booking details changed multiple times via corrections.

Knowledge base hot-reload

Hospital information (timings, departments, policies, payment details) is stored in data/hospital_knowledge.json. When the admin dashboard updates this file via PATCH /api/knowledge, the handler invalidates the in-memory cache (_hospital_knowledge = None) so the next LLM call picks up the new values without restarting the server.

Section 16

Booking & Database

The database uses SQLite via SQLModel (a Pydantic + SQLAlchemy wrapper). Tables: Appointment, Doctor, Department, DoctorSlot. The database file lives at data/appointments.db.

Slot availability is computed from DoctorSlot records (which define a doctor's weekly available hours) minus Appointment records that are already confirmed for that doctor and date. The BookingSystem.get_available_slots() method returns time strings like "09:00 AM" for the next 5 days.

When the LLM returns action="save" (or the Fast Engine returns action="save" for an affirmative confirmation), _execute_booking() writes the appointment to the database and returns a speech response that includes the booking ID. The LLM is not involved in the write — it only decides when all required information is present and confirmed.

After booking, the system tells the caller they will receive a WhatsApp message and should send a screenshot of the fee payment. This WhatsApp message is sent manually by the hospital admin, not automatically. Sara only informs the caller it is coming.

Section 17

WebSocket Server

Each call session opens a WebSocket connection to /ws/call/{session_id}. The server runs two concurrent loops per connection via asyncio.gather(receive_loop(), send_loop()).

receive_loop reads incoming WebSocket frames. Binary frames are audio chunks passed to handler.process_audio_chunk(). Text frames are JSON control messages; an end_call message from the browser terminates the loop. The loop exits when the handler becomes inactive (while handler.is_active) — which happens when the caller disconnects, says goodbye, or the inactivity monitor fires.

send_loop drains handler.consume_responses(). Binary items are sent as WebSocket binary frames (raw audio). JSON items are sent as text frames. The browser receives these frames and either plays the audio or updates the UI (transcript display, status indicator, etc.).

After both loops exit, the server sends a final {"type":"call_ended"} message and the WebSocket connection closes. A finally block always calls handler.end_call() to cancel background tasks, save the call log, and release the session from the active-calls registry regardless of how the call ended.

Call logs are saved to data/call_logs/{date}_{session_id}.json on every call end. They contain the full transcript, the collected booking fields, and the final flow state — useful for debugging why a call did not complete a booking.
